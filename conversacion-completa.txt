## Evaluación: ¿Qué tan complicado es adaptar Resumint a varios idiomas?

**Respuesta corta: Es un trabajo grande, pero muy factible y bien estructurado.**

---

### El estado actual

El proyecto tiene **70 archivos** (app + components) con todo el texto en español hardcodeado directamente en el JSX. No existe ninguna librería ni infraestructura de i18n instalada. Cero. Ni una carpeta de traducciones.

---

### Dónde está el trabajo real

| Área | Complejidad | Detalle |
|---|---|---|
| Páginas UI (53 archivos) | Alta | ~400–600 strings en JSX, ternarios, arrays de objetos |
| Componentes (17 archivos) | Media | Sidebar, Header, botones, labels |
| Prompts de IA (9 prompts) | Muy alta | Instrucciones completas en español, requieren revisión manual por idioma |
| Lógica de negocio | Media | Lista de soft skills hardcodeada en español (31 keywords para clasificación) |

El problema más delicado son los **prompts de IA** — no es solo traducir texto, es decidir si la IA debe responder en el idioma del usuario o siempre en español. Los prompts tienen lógica embebida en el idioma.

---

### Estimación realista

- **Solo inglés + español:** ~40–50 horas
  - Setup de `next-intl` (la librería correcta para App Router de Next.js)
  - Extracción y organización de keys
  - Refactor de los 70 archivos
  - Decisión arquitectural sobre los prompts de IA

- **Cada idioma adicional después del primero:** ~5–8 horas (solo traducción, la infraestructura ya está)

---

### Lo que haría diferencia

1. **next-intl** es la opción obvia — tiene soporte nativo para Next.js 14+ App Router, type-safety, y manejo de namespaces
2. Los prompts de IA deberían **quedarse en español por ahora** si el mercado objetivo es latinoamérica — añadir una capa de idioma en los prompts multiplica los costos de tokens y la complejidad
3. La base de datos (nombres de campos, valores como `'En espera'`, `'Entrevistando'`) necesita decisiones sobre si los estados se guardan en código o en el idioma del usuario

**Veredicto:** No es trivial, pero tampoco es una reescritura. Es un refactor sistemático sin cambios de lógica. Si el mercado objetivo en el corto plazo es hispanohablante, yo lo postpondría hasta validar tracción.

pregunta: Es sabido que los prompts en ingles, siempre son mejores y mas efectivos que los prompts en cualquiero otro idioma, no es posible estandarizar el uso del ingles para todos los prompts pero pidiendole que responda en el idioma del usuario? es decir, si el perfil de un usuario esta en español, aunque el prompt este en ingles, el resultado se darà en español.

=== CLAUDE ===
Sí, exactamente — y es la práctica estándar en producción.

---

### Cómo funciona

Los LLMs (Claude incluido) separan completamente el **idioma de las instrucciones** del **idioma de la respuesta**. Puedes escribir:

```
You are a professional CV writer. Extract and reorganize the user's work experience 
to highlight measurable achievements. Be concise and impactful.

IMPORTANT: Always respond in the same language as the user's profile data.
```

Y si los datos del usuario están en español, el output sale en español. Si están en inglés, en inglés. Claude es especialmente bueno en esto — el razonamiento interno ocurre en el idioma más fuerte del modelo (inglés), pero la salida sigue la instrucción de idioma.

---

### Por qué funciona bien para Resumint en particular

Tu caso es ideal para este patrón porque:

1. **Los datos del usuario ya dictan el idioma** — si alguien puso "Desarrollador Senior en Empresa XYZ" en su perfil, el CV va a salir en español naturalmente, con o sin instrucción explícita
2. **Los CVs son documentos en el idioma del usuario** — nadie quiere un CV en un idioma diferente al que escribió su experiencia
3. **La instrucción de idioma es una sola línea** por prompt — costo cero en tokens y complejidad

---

### La instrucción que yo usaría

```
Respond exclusively in the same language as the user's profile data. 
If the profile contains mixed languages, default to Spanish.
```

Esto cubre el caso edge de perfiles mezclados (común en usuarios bilingues).

---

### Conclusión práctica

Para Resumint, la estrategia correcta es:
- **Todos los prompts en inglés** (mejor calidad de razonamiento)
- **Una línea al final de cada prompt** indicando que responda en el idioma de los datos
- **Cero cambios en la base de datos ni en la UI** para soportar múltiples idiomas a nivel de IA

Esto significa que si mañana quieres soportar inglés, francés o portugués, los prompts ya están listos — solo necesitas traducir la UI.

Buena pregunta de arquitectura. Hay tres enfoques, con tradeoffs claros:

---

**Opción A — Templates como datos en DB (completamente sin código)**
Cada template se define como JSON en Supabase: colores, fuente, orden de secciones, espaciado, tipo de layout. Un único componente "renderer" universal lee ese JSON y renderiza cualquier template.

- ✅ Admin agrega templates sin tocar código
- ❌ Limitado: solo puedes hacer variaciones de los layouts que ya están programados. Un diseño radicalmente diferente (sidebar, timeline, doble columna) requiere programar ese tipo de layout primero

---

**Opción B — Templates como código + metadata en DB (lo que tienes hoy)**
El componente React es código, pero todo lo demás (nombre, descripción, "ideal para", precio, activo/inactivo, orden) vive en Supabase y se administra desde el panel.

- ✅ Flexibilidad de diseño ilimitada por template
- ❌ Cada template nuevo siempre requiere un developer

---

**Opción C — Híbrido por "tipo de layout" (la que recomiendo)**
Programas una vez cada tipo estructural de layout: `single-column`, `two-column-sidebar`, `timeline`, `executive-header`. Dentro de cada tipo, todos los valores visuales (paleta, tipografía, proporciones, orden de secciones) son configurables desde el admin como JSON.

- ✅ Nuevos templates dentro de layouts existentes = solo admin, cero código
- ✅ Si necesitas un layout radicalmente nuevo, lo programas una vez y queda disponible para infinitos templates
- ✅ Escala a cientos de templates sin deuda técnica
- ❌ Requiere más trabajo inicial para construir el sistema de configuración

## Cómo funcionan los estilos de CV General y CV Vacante

### El flujo de datos (de punta a punta)

```
/create-cv → sessionStorage['cv_params'] → /create-cv/preview
    → POST /api/generate-cv → Claude Haiku 4.5 → JSON → DB (cvs)
    → CVRenderer → ClassicCV | ModernCV | MinimalCV | BoldCV | ExecutiveCV
```

---

### 1. El JSON que produce la IA

Todos los prompts (P4–P7) piden exactamente esta estructura:

```typescript
interface CVData {
  nombre: string
  titulo: string
  resumen: string
  contacto: { email, telefono?, ubicacion? }
  experiencias: [{ empresa, cargo, fecha_inicio, fecha_fin?, descripcion? }]
  educacion:    [{ institucion, titulo, area?, fecha }]
  habilidades:  string[]
  idiomas:      [{ nombre, nivel? }]
  logros:       string[]
}
```

Ese mismo objeto va al DB en `contenido_json` y lo consumen directamente los 5 templates.

---

### 2. Los 5 templates — layout de cada uno

| Template | Layout | Particularidad |
|---|---|---|
| **ClassicCV** | 1 columna | Header con línea separadora, todo formal |
| **ModernCV** | 2 columnas | Sidebar de color con contacto + habilidades |
| **MinimalCV** | 1 columna | Muy espaciado, uppercase tracking-widest en headers |
| **BoldCV** | Header dark + contenido | Nombre en text-5xl, border-left-4 colored en secciones |
| **ExecutiveCV** | 2 columnas premium | Sidebar oscuro (w-80), ◆ en logros, tono senior |

Todos reciben las mismas props: `data: CVData`, `isEditMode: boolean`, `onFieldChange`, `accentColor?: string`.

### 3. Los prompts (P4–P7) — están hardcoded en el API route

**Esta es la parte importante:** los prompts P4–P7 **no son archivos separados** — están construidos dinámicamente dentro de `app/api/generate-cv/route.ts`. La función `buildPrompt()` los arma según:

- `mode`: `'general'` o `'job'`  
- `hasExperience`: si hay entradas en tabla `experiencia`
- `estilo`: inyecta instrucciones de estilo como variable

Las instrucciones de estilo son cadenas cortas (1 línea cada una):
```
classic:   "Estructura clásica: encabezado con nombre/contacto, secciones con línea separadora..."
modern:    "Estructura moderna: colores sutiles, jerarquía visual clara, frases de impacto..."
minimal:   "Estructura minimalista: solo lo esencial, máximo espacio en blanco..."
bold:      "Estructura bold: cargo destacado, logros cuantificados, lenguaje de acción..."
executive: "Estructura ejecutiva: perfil senior, resumen ejecutivo prominente, logros estratégicos..."
```

El estilo **no cambia la estructura del JSON** — solo cambia el tono del texto que la IA escribe.

---

### 4. Personalización de color

En el preview, el usuario puede cambiar el `accentColor` con un picker de 5 swatches + hex manual. Ese color se pasa como prop a todos los templates, que lo usan para headings, borders y elementos de énfasis.

---

### 5. Lo que distingue CV General vs CV Vacante

La única diferencia real es el prompt:
- **General:** titulo = `profesion_perfil` del usuario
- **Vacante:** titulo = cargo objetivo de la vacante; el texto de la vacante se inyecta en `<vacante>` tags para que la IA alinee el CV con esas keywords (ATS)

El template renderizado es idéntico en ambos casos.

---

### Problemas clave para la unificación con CV Studio

1. **Los prompts están hardcoded** en la route, no en `/lib/prompts/`. Difícil mantener.

2. **Las instrucciones de estilo son 1 línea** — influyen en el tono del texto, no en el diseño visual. El diseño lo controlan los componentes React, que son estáticos.

3. **Sin foto** en ningún template de CV General/Vacante (a diferencia de Mirror).

4. **Dos sistemas completamente separados:** los 5 templates usan `CVData`, Mirror usa `MirrorDiseno + MirrorContenido` con layout dinámico.

### La respuesta a tu pregunta original

> "¿Cómo agregar nuevos estilos sin tocar código?"

Hoy no es posible. Para agregar un nuevo estilo de CV General/Vacante necesitas:
1. Crear un nuevo componente React (ej. `CreativeCV.tsx`)
2. Registrarlo en `components/CVTemplates/index.tsx`
3. Agregar su instrucción de estilo en `generate-cv/route.ts`
4. Agregarlo a la lista de estilos en el wizard

CV Studio ya resuelve esto de forma diferente: los templates se cargan desde DB con `MirrorDiseno` como JSON de configuración — sin código. Ese es el modelo que habría que replicar si quieres que General/Vacante también sea extensible sin tocar código.

## Principios de diseño

**Una función por componente. Sin excepciones.**
El sistema actual tiene un prompt que simultáneamente recibe datos sucios, analiza un estilo, decide cómo escribir, y genera el JSON. Eso es exactamente lo que vamos a eliminar.

**Lo determinístico no lo hace la IA.**
Limpiar datos, validar estructura, seleccionar el pipeline correcto — eso no necesita IA. La IA solo entra donde su capacidad de generar lenguaje natural es irreemplazable.

**Cada estilo tiene una guía de escritura real, no un label.**
"Estructura ejecutiva" no le dice nada a la IA. "Usa framing de P&L, menciona escala organizacional, cada experiencia requiere un resultado estratégico cuantificado" sí le dice algo.

## Las 5 capas del pipeline

### Capa 1 — Preparación de datos `(determinístico)`
```
prepareUserData(userId) → CVUserData
```

Hoy la IA recibe objetos crudos de Supabase con `id`, `user_id`, `created_at`, etc. Esta capa:
- Elimina todos los campos de DB metadata
- Normaliza `fecha_fin: null` → `"Presente"`

- Devuelve un objeto `CVUserData` limpio y tipado

### Capa 2 — Configuración de estilo `(determinístico)`
```
getStyleConfig(estilo) → StyleConfig
```

Esta es la pieza central de todo el rediseño. Hoy el estilo es 1 línea. La nueva `StyleConfig` es una guía de escritura completa:

```typescript
interface StyleConfig {
  id:                   string
  nombre:               string
  writingTone:          'formal' | 'narrative' | 'technical' | 'strategic' | 'comprehensive'
  resumeInstructions:   string   // cómo estructurar el resumen exactamente
  experienceFormat:     string   // cómo escribir cada descripción
  requiredElements:     string[] // qué no puede faltar en este estilo
  vocabulary:           string[] // verbos y palabras a usar
  avoid:                string[] // frases y construcciones a evitar
  prioritySections:     string[] // qué secciones son más importantes en este estilo
}
```

**Cada estilo, desarrollado como su propio estándar:**

**Harvard:**
- Resumen: 3 frases. Años de experiencia + función principal. Un logro cuantificado. Qué aporta al siguiente rol.
- Experiencia: cada descripción empieza con verbo de acción + resultado medible. Ejemplo: "Incrementó las ventas regionales un 34% restructurando el proceso de captación."
- Obligatorio: al menos 1 métrica por experiencia ($, %, personas, tiempo)
- Vocabulario: lideró, gestionó, incrementó, redujo, implementó, optimizó
- Evitar: "responsable de", "participé en", "apoyé", "colaboré"

**Stanford:**
- Resumen: narrativo, propósito + trayectoria + impacto creado. Voz humana, no corporativa.
- Experiencia: formato mini-historia. Contexto (por qué importaba) → acción tomada → resultado o aprendizaje
- Obligatorio: contexto y relevancia de cada decisión
- Vocabulario: construyó, lanzó, transformó, impulsó, mentoreó, colaboró
- Evitar: listas secas de tareas, lenguaje pasivo

**Europeo:**
- Resumen: comprensivo, cubre perfil + competencias + objetivo profesional
- Experiencia: sistemática y completa, cubre todas las responsabilidades, no solo logros
- Obligatorio: idiomas con nivel formal (B1, B2, C1), todas las secciones rellenas
- Vocabulario: responsable de, coordinó, gestionó, desarrolló, participó en
- Tono: neutral, oficial, sin hipérbole

**Silicon Valley:**
- Resumen: máximo 2 frases. Stack tecnológico + impacto a escala. Extremadamente directo.
- Experiencia: especificidad técnica obligatoria. Stack usado + métrica de escala (usuarios, requests/seg, TB) + decisión técnica tomada
- Obligatorio: stack mencionado, al menos 1 métrica de escala técnica por experiencia
- Vocabulario: shipped, built, architected, scaled, deployed, optimized, reduced latency
- Evitar: soft skills, descripciones vagas, adjetivos sin datos

**Ejecutivo:**
- Resumen: formato executive summary. Alcance (industrias, funciones) + Escala (personas, presupuesto, revenue) + Impacto estratégico
- Experiencia: framing de negocio. "Dirigió equipo de X personas, gestionó presupuesto de $X, entregó $X en ingresos"
- Obligatorio: escala organizacional en cada experiencia, outcome estratégico
- Vocabulario: dirigió, transformó, expandió, reestructuró, supervisó P&L

### 1 — El límite de logros / bullets

Primero hay que separar dos cosas que el research mezcla:

- **Bullets dentro de cada experiencia laboral** — Harvard dice 3-5 por entrada. Eso es sobre la descripción de cada cargo, no sobre la sección de logros.
- **Sección "Logros" standalone** — Esta es diferente. Aquí no hay un límite rígido.

Para los bullets de experiencia, el límite existe por una razón real: un reclutador escanea en 15 segundos. Si un cargo tiene 9 bullets, ninguno se lee bien. La regla del research es correcta aquí.

Pero la solución no es cortar logros importantes — es **priorizarlos por impacto**. La instrucción correcta para la IA:

```
Experience bullets: 3-5 per role. Most recent role gets 4-5, older roles get 2-3.
If the user has more achievements than the limit allows, rank by magnitude of impact
and include only the highest-impact ones. Never cut an achievement arbitrarily —
cut by relevance and impact order.

For CV Vacante: rank bullets by relevance to the target vacancy first, then by magnitude.
```

Esto significa que si el usuario tiene 8 logros reales en un cargo, la IA incluye los 4-5 más poderosos (o más relevantes para la vacante), no los primeros 4 de la lista.

## Las 7 StyleWritingConfigs — Diferencias clave

Este es el núcleo del sistema. Un resumen de lo que cada config define:

**Harvard**
- Verbo pasado simple obligatorio. Sin primera persona. Sin adjetivos.
- Fórmula: `[Verbo acción] + [tarea] + [resultado cuantificado] + [contexto]`
- Cada bullet: mínimo 1 métrica ($, %, headcount, tiempo)
- 4-5 bullets en rol más reciente, 2-3 en roles anteriores
- Summary: opcional o máximo 3 líneas. La mayoría de Harvard CVs fuertes lo omiten.
- Prohibido: "responsable de", "participé en", voz pasiva, adjetivos autopromocionales

**Stanford**
- Híbrido: verbos Harvard + vocabulario tech moderno permitido
- Permite variación: bullet puede iniciar con nombre de producto si clarifica
- Selected Projects es sección estructural, no opcional
- Summary: 2-3 líneas para mid-senior con narrativa clara
- Metrics: DAU/MAU, NPS, latency, conversion rates además de $/%

**Silicon Valley**
- Máximo 2 líneas de Summary. La mayoría lo omite.
- Especificidad técnica obligatoria: stack + métrica de escala en cada bullet
- Métricas: p99 latency, QPS, MAU, uptime %, $ ahorro en infra
- Sin "Spearheaded", sin "Drove" repetido — demasiado corporativo para este contexto
- Skills/Tech Stack como sección independiente prominente

**Tech Resume**
- Balance entre técnico y business context — ni tan raw como SV ni tan corporativo como Harvard
- Tech Stack primero, antes de Experience
- Métricas mezcladas: técnicas (latency, throughput) + business (retention %, cost reduction)
- Más convencional en formato, más mainstream en audiencia

**Minimalista Moderno**
- Cada palabra gana su lugar. Si no aporta señal, se elimina.
- Verbos específicos de diseño: Designed, Crafted, Shaped, Defined, Prototyped
- Positioning line (1 frase) en lugar de Summary tradicional
- Métricas de impacto de diseño: conversion %, design system adoption, team size
- Prohibido: "Drove", "Spearheaded" — demasiado Executive/Harvard en tono

**Europass**
- Estilo descriptivo, no persuasivo. Infinitivos o tercera persona impersonal.
- Métricas con texto descriptivo completo: no "↑34%" sino "incremento del 34%"
- Formato numérico europeo: coma decimal, punto miles, € después del número
- CEFR obligatorio para idiomas: A1-C2 por competencia
- Prohibido: autopromocional, superlatives, lenguaje tipo elevator pitch

**Executive**
- Executive Summary obligatorio: 4-7 líneas con scope + scale + top achievements
- Areas of Expertise como grid de keywords (8-15)
- Métricas de escala organizacional: revenue, EBITDA, headcount, M&A value, TSR
- Cada experiencia: 1-2 líneas de contexto de empresa + 4-7 bullets achievement
- Bold parcial en métricas clave (la IA debe marcarlas como `**$3.2B**`)

## Las reglas globales (por encima de todo)

Estas van al inicio de cada prompt, antes de cualquier StyleWritingConfig:

```
GLOBAL RULES — these override any style-specific instruction:

LANGUAGE: Detect the primary language from the user's profile data.
Write the ENTIRE CV in that language. These instructions are in English
for precision; your output must always match the user's data language.

PROFESSIONAL TITLE: The header ALWAYS follows this structure:
  Line 1: Full name (largest typographic element)
  Line 2: Professional title
    - CV General → exact value of profesion_perfil
    - CV Vacante → exact job title from the vacancy posting
  Line 3: Contact information
This structure is non-negotiable regardless of style.

DATA INTEGRITY: Use ONLY real information from the user's profile.
Do not invent experience, skills, achievements, dates, or employer names.
If a section has no data and no fallback is possible, omit it entirely.
An empty section is better than an invented one.

OUTPUT FORMAT: Return ONLY valid JSON. No markdown. No explanation.
No text before or after the JSON object.
```

// app/api/generate-cv/route.ts — ~50 líneas
export async function POST(request: NextRequest) {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return unauthorized()
  if (!rateLimit(user.id, 5, 60_000)) return tooManyRequests()
  
  const { mode, estilo, descripcion_vacante } = await request.json()
  if (!mode || !estilo) return badRequest('Missing params')
  if (!VALID_STYLES.includes(estilo)) return badRequest('Invalid style')
  if (mode === 'job' && !descripcion_vacante) return badRequest('Missing vacancy')
  
  const anthropic = createAnthropicClient()
  
  const result = mode === 'general'
    ? await generalPipeline(user.id, estilo, supabase, anthropic)
    : await vacancyPipeline(user.id, estilo, descripcion_vacante, supabase, anthropic)
  
  return NextResponse.json(result)
}
